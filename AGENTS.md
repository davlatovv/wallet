# Repository Guidelines

## Project Structure & Module Organization

This repository is a Python 3.11+ Telegram finance bot. `main.py` is the entry point and starts migrations, aiogram, and APScheduler. Core code lives in `app/` and follows a layered flow: `domain/` for dataclass entities, value objects, exceptions, and abstract repositories; `application/` for DTOs, interfaces, and use cases; `infrastructure/` for SQLAlchemy models, repository implementations, database sessions, exports, currency clients, and notifications; `presentation/telegram/` for handlers, keyboards, states, filters, middlewares, and router wiring. Alembic configuration is in `alembic.ini`, with migrations in `db/migrations/versions/`. Runtime exports are written under `exports/`.

## Build, Test, and Development Commands

- `python -m venv .venv && source .venv/bin/activate`: create and activate a local virtual environment.
- `pip install -e ".[dev]"`: install the app plus pytest tooling from `pyproject.toml`.
- `docker-compose up --build`: run PostgreSQL and the bot together.
- `alembic upgrade head`: apply database migrations when running services manually.
- `python main.py`: start the bot locally; requires `.env` with `BOT_TOKEN` and `DATABASE_URL`.
- `pytest`: run the test suite. Use `pytest -x` to stop at the first failure.

## Coding Style & Naming Conventions

Use 4-space indentation, type hints, and async/await consistently. Keep layer dependencies one-way: domain must stay framework-free; application should not import ORM or aiogram types; presentation should call use cases through `Container`, not query the database directly. Name modules by feature in snake_case, for example `manage_budgets.py`, `add_expense.py`, and `excel_exporter.py`. Alembic migrations use the existing `NNNN_description.py` pattern.

## Testing Guidelines

Tests should use `pytest`, `pytest-asyncio`, and `pytest-mock` from the dev dependencies. Place tests in a top-level `tests/` package mirroring the source area being covered. Prefer focused unit tests for domain value objects and use cases, and mock repositories or external services such as Telegram, CBU currency requests, and schedulers. Name files `test_<feature>.py` and test functions `test_<expected_behavior>`.

## Commit & Pull Request Guidelines

Recent history uses short imperative commit subjects, for example `Add debt selection logic...` and `Update deploy workflow...`. Keep commits focused. Pull requests should include a concise summary, migration notes when schema changes are present, local test results, linked issues if applicable, and screenshots or Telegram interaction notes for presentation changes.

## CI/CD Deployment

GitHub Actions runs on pushes and pull requests to `master`. The `lint` job checks Python syntax with `py_compile`. On push to `master`, the `deploy` job connects to the VPS via SSH, pulls the latest code in `/home/wallet`, restores the existing `.env`, and runs `docker compose up -d --build --remove-orphans`. Required repository secrets are `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, and `VPS_PORT`.

## Security & Configuration Tips

Do not commit `.env` or secrets. Required local settings include `BOT_TOKEN` and asyncpg-style `DATABASE_URL`; optional settings include `LOG_LEVEL`, `TIMEZONE`, and `DEBUG`. Review autogenerated migrations before applying them, especially changes to money fields stored as UZS `Decimal` values.
